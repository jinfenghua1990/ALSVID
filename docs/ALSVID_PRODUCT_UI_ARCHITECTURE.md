# ALSVID 产品 UI 与业务架构规范

## 1. UI 方向

ALSVID 后台采用品牌化产品平台设计，不采用传统 ERP 左侧菜单风格。

设计原则：

- 顶部一级导航，体现国际品牌平台感
- 页面视觉参考 Tesla / Apple / DJI 等产品型网站
- 后台功能保持专业，但突出产品展示和生命周期管理
- 复用 CoffeeBear 已验证的 UI 设计语言，但不复制业务逻辑

## 2. 一级导航

推荐结构：

- 首页
- 产品中心
- Vehicle 360
- 订单管理
- 经销商
- 售后服务
- 配件 BOM
- 客户中心
- 系统设置

## 3. 产品中心 Product Center

产品中心是 ALSVID 产品主数据的唯一维护入口，负责区分技术平台、商业车型与工程发布事实。

### 3.1 技术平台（固定顺序）

1. **FC Platform — Folding Carbon**：碳纤维折叠平台
2. **CT Platform — City Touring**：都市通勤平台
3. **FT Platform — Fat Tire**：胖胎平台
4. **GT Platform — Gravel/Touring**：Gravel 与长途旅行平台

技术平台不是具体车型。页面展示顺序固定为 FC → CT → FT → GT，不依赖数据库默认排序。

### 3.2 产品与工程数据层级

`Platform → Model → Variant → SKU`

- **Model**：具体车型，例如 FC1、FC1 Pro、CT1、FT1、GT1；车型字段包括平台、型号代码、名称、状态和记录版本。
- **Variant**：车型的商业配置版本，例如 Standard、Pro。
- **SKU**：可销售配置身份，可关联市场、颜色、尺寸等属性。
- **BOM**：关联具体车型；BOM Revision 负责工程版本及草稿/发布状态。
- **Build Specification**：将 SKU 与已发布的 BOM Revision 关联，形成受控生产规格。
- **零部件与工程资料**：由工程主数据管理，并通过明确的关联关系追溯到 BOM 或产品对象。

### 3.3 型号总表与数据状态

型号总表至少展示：**型号、技术平台、配置版本、产品状态、当前工程阶段、关联 BOM、操作**。

- “当前工程阶段”必须根据真实 BOM Revision 和 Build Specification 状态计算，不得把普通记录版本直接解释为量产阶段。
- 型号、SKU、BOM 或零部件数量必须来自 API 的真实返回值。
- 页面加载中显示加载状态；API 请求失败要单独显示错误；只有 API 成功返回空集合时才显示“暂无数据”。
- 不创建虚构的 FC1、CT1 等演示记录来掩盖正式数据库为空的问题。

### 3.4 后续业务联动边界

当前产品中心负责产品主数据和工程规格。后续应按真实外键/业务关联打通：

`产品型号 → 配置版本 → SKU → BOM / Build Specification → 生产订单 → 库存 → 销售订单`

生产、库存、订单等下游环节只有在接口和关联键实际接通并验证后，才能显示为已联动；尚未完成的环节必须明确标注待接入，不以静态卡片代替业务闭环。

产品中心管理“卖什么产品”以及对应的受控工程规格；渠道系统可以映射 SKU，但不能反向覆盖 ALSVID 产品主数据。

## 4. Vehicle 360 定义

当前阶段 Vehicle 360 不定义为智能车辆监控。

原因：

- 自行车没有联网
- 没有实时 GPS
- 没有 BMS 数据上传
- 没有 OTA
- 没有实时健康检测

因此 Vehicle 360 定义为：

> 车辆全生命周期档案管理

管理对象：已经生产、销售出去的真实车辆。

## 6. 单车档案

每台车辆通过 VIN / 车架号建立档案。

包含：

- 基础信息
- 型号
- 配置
- 生产批次
- 供应商
- 质检记录
- 物流记录
- 销售记录
- 客户信息
- 售后维修记录

## 7. 暂不实现功能

以下功能未来智能化阶段再扩展：

- 实时车辆定位
- 电池健康监测
- 电机状态监控
- APP连接
- OTA升级

## 8. 首页 Dashboard

首页重点展示：

- 产品系列
- SKU数量
- 订单状态
- 经销商数量
- 售后任务
- 产品运营数据

不突出实时车辆健康数据。

## 9. 长期扩展

未来如果增加智能硬件能力，可升级：

Vehicle 360+

增加：

- 智能状态
- 数据回传
- APP绑定
- 远程诊断

当前架构无需推翻。
