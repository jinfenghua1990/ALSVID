# ALSVID 产品 UI 与业务架构规范

## 1. UI 方向

ALSVID 后台采用品牌化产品平台设计，不采用传统 ERP 左侧菜单风格。

设计原则：

- 顶部一级导航，体现国际品牌平台感
- 页面视觉参考 Tesla / Apple / DJI 等产品型网站
- 后台功能保持专业，但突出产品展示和生命周期管理
- 复用 CoffeeBear 已验证的 UI 设计语言，但不复制业务逻辑

## 2. 一级导航

推荐结构：

- 首页
- 产品中心
- Vehicle 360
- 订单管理
- 经销商
- 售后服务
- 配件 BOM
- 客户中心
- 系统设置

## 3. 产品中心 Product Center

产品中心是 ALSVID 产品主数据的唯一维护入口，负责区分技术平台、商业车型与工程发布事实。

### 3.1 技术平台（固定顺序）

1. **FC Platform — Folding Carbon**：碳纤维折叠平台
2. **CT Platform — City Touring**：都市通勤平台
3. **FT Platform — Fat Tire**：胖胎平台
4. **GT Platform — Gravel/Touring**：Gravel 与长途旅行平台

技术平台不是具体车型。页面展示顺序固定为 FC → CT → FT → GT，不依赖数据库默认排序。

### 3.2 产品与工程数据层级

`Platform → Model → Variant → SKU`

- **Model**：具体车型，例如 FC1、FC1 Pro、CT1、FT1、GT1；车型字段包括平台、型号代码、名称、状态和记录版本。
- **Variant**：车型的商业配置版本，例如 Standard、Pro。
- **SKU**：可销售配置身份，可关联市场、颜色、尺寸等属性。
- **BOM**：关联具体车型；BOM Revision 负责工程版本及草稿/发布状态。
- **Build Specification**：将 SKU 与已发布的 BOM Revision 关联，形成受控生产规格。
- **零部件与工程资料**：由工程主数据管理，并通过明确的关联关系追溯到 BOM 或产品对象。

### 3.3 型号总表与数据状态

型号总表至少展示：**型号、技术平台、配置版本、产品状态、当前工程阶段、关联 BOM、操作**。

- “当前工程阶段”必须根据真实 BOM Revision 和 Build Specification 状态计算，不得把普通记录版本直接解释为量产阶段。
- 型号、SKU、BOM 或零部件数量必须来自 API 的真实返回值。
- 页面加载中显示加载状态；API 请求失败要单独显示错误；只有 API 成功返回空集合时才显示“暂无数据”。
- 不创建虚构的 FC1、CT1 等演示记录来掩盖正式数据库为空的问题。

### 3.4 后续业务联动边界

当前产品中心负责产品主数据和工程规格。后续应按真实外键/业务关联打通：

`产品型号 → 配置版本 → SKU → BOM / Build Specification → 生产订单 → 库存 → 销售订单`

生产、库存、订单等下游环节只有在接口和关联键实际接通并验证后，才能显示为已联动；尚未完成的环节必须明确标注待接入，不以静态卡片代替业务闭环。

产品中心管理“卖什么产品”以及对应的受控工程规格；渠道系统可以映射 SKU，但不能反向覆盖 ALSVID 产品主数据。

## 4. Vehicle 360 定义

当前阶段 Vehicle 360 不定义为智能车辆监控。

原因：

- 自行车没有联网
- 没有实时 GPS
- 没有 BMS 数据上传
- 没有 OTA
- 没有实时健康检测

因此 Vehicle 360 定义为：

> 车辆全生命周期档案管理

管理对象：已经生产、销售出去的真实车辆。

## 6. 单车档案

每台车辆通过 VIN / 车架号建立档案。

包含：

- 基础信息
- 型号
- 配置
- 生产批次
- 供应商
- 质检记录
- 物流记录
- 销售记录
- 客户信息
- 售后维修记录

## 7. 暂不实现功能

以下功能未来智能化阶段再扩展：

- 实时车辆定位
- 电池健康监测
- 电机状态监控
- APP连接
- OTA升级

## 3.5 天猫式商品 ID 与 SKU 交互（已确认）

采用“一个商品主记录、一个详情页、多个 SKU”的模式。此处的商品主记录对应 Model：

- **商品 ID**：Model 的稳定数据库 ID。同一详情页下所有颜色、市场、尺寸及版本 SKU 都归属同一个 Model ID。
- **Variant**：商品详情页内的商业版本选项，例如 Standard / Pro。
- **SKU**：用户最终选中的可销售组合；SKU 编码唯一，按实际销售维度区分，例如颜色、市场、尺寸。
- **切换颜色/版本**：商品 ID 不变；当前 SKU 必须同步变化。商品图、价格、库存、可购买状态只能由对应的已接入数据源提供；未接通时明确显示待接入，不得虚构联动。
- **购物车和订单**：每一行必须保存具体 SKU ID / SKU 编码、数量和下单时适用的价格快照；不能只保存商品 ID。库存预留由 Inventory 负责，订单归 Commerce，价格归 Commerce/价格策略的正式所有者。
- **后台产品总表**：显示商品 ID、型号、技术平台、版本、状态、工程阶段和 BOM；商品 ID 与 SKU 必须明确分列或分层展示。
- **后台商品结构树**：以商品 ID 为父级，把 Variant 与 SKU 归组显示；SKU 行展示 SKU 编码、颜色、市场、尺寸和状态。
- **新建 SKU**：先选商品下的 Variant，再填写唯一 SKU 编码和维度属性；服务端唯一约束仍是最终防重依据。
- **编辑和停用**：沿用版本号并发校验、权限检查、审计与保存后重读核对；已被订单/工程引用的记录不通过删除来“清理”，应按领域规则退役。
- **后续商品发布交互**：商品资料、图片/素材、德英中文案、审核发布状态分别维护。产品 ACTIVE 不等于公开发布；WWW 只读取经过审核的公开目录。
- **边界**：商品 ID 不等于 VIN；商品 SKU 不等于零部件 Part Number。BOM/Build Spec、库存、价格、订单与售后继续由各自领域维护权威事实。
