# ALSVID 单一系统与多 AI 协作强制契约

> **状态：active / 2026-10-26 / 负责人确认**。本文件是所有参与 ALSVID 开发、修改、测试、集成、发布的 AI/Agent/开发人员必须遵守的产品与工程约束。入口：仓库根目录 `AGENTS.md`。
>
> **核心约束：一个 ALSVID、一份代码权威、一套业务事实、持续联动；多个机器人只是同时编辑同一套系统，不是独立开发多套再事后拼接。**

## 1. 系统身份：不可拆成互不相关的产品

1. **唯一代码权威**：`jinfenghua1990/ALSVID` 是 ALSVID 的唯一实现仓库。现有 `pnpm-workspace.yaml`（`apps/*`、`packages/*`、`domains/*`）是统一工程工作区。不得为 Admin、订单、生产、库存、售后等业务再创建独立的权威仓库、孤立工程、单独的锁文件或第二套系统。
2. **模块化单体（Modular Monolith）**：`apps/web`、`apps/api`、`apps/worker` 是**一套 ALSVID** 的不同运行进程/容器，不是三套独立业务系统；领域模块通过现有公共契约/事件集成，不能复制业务逻辑和数据写入权威。
3. **前端门户边界依然有效**：Official、Admin、Dealer、My（及分阶段 Supplier）可以具备独立用户体验、入口和鉴权范围，但仍接入 ALSVID 统一身份/业务事实/授权 API；**禁止**为某门户再搭独立业务数据库、同义订单系统、会员身份库或售后主账。不同门户的安全和数据范围不能因代码共仓而被取消。
4. **一份正式业务事实**：生产结构化数据由 Neon PostgreSQL 承载，文件由 Cloudflare R2 承载。按 `docs/DATA_OWNERSHIP.md` 确定各领域表与写入权威。禁止跨领域直接修改别人的表、复制数据库来“解决集成”；读取可走公共查询契约或明确只读投影。不得让本地/CI/机器人使用生产密钥测试。
5. **容器化不是拆系统**：Docker 的作用是将同一套程序可重复地启动于不同授权环境。Cloud Run 是当前选用的生产运行平台，不是应用代码必须绑定的业务前提。可移植的一键 Docker 启动尚需独立实现与验收，不得声称已有此能力。

## 2. 多机器人分工：按功能开发，但代码从第一天就联动

1. 每个机器人开工先读取最新 `main`、`AGENTS.md`、**本契约**、`docs/ARCHITECTURE.md`、`docs/DOMAIN_STRUCTURE.md`、`docs/DATA_OWNERSHIP.md`、`docs/BUSINESS_FLOWS.md`、`docs/CURRENT_STATE.md`、相关 ADR / Issue / PR。不能从旧聊天内容或未经核实的记忆推断当前代码状态。
2. 可以分别处理产品/BOM、生产、库存、订单、车辆/VIN、售后、财务等任务，但每个任务必须使用**同一仓库和现有模块**，从当前主干短分支开发，及时通过 PR 集成；禁止机器人各自做一份完整产品，最后交给“合并机器人”重新发明对接方法。
3. 业务改动开始前，列明 **上游来源 → 本次领域写入权威 → 下游消费方**，以及引用的 SKU、BOM 修订、生产单、库存台账、订单、Vehicle/VIN、车主、工单等统一 ID/状态契约。先校准跨模块接口，再实现页面和功能。
4. 影响多个模块的一次功能改动应在**同一 PR** 更新必要的数据迁移、领域契约/API、前后端调用和回归测试；确实分成依赖 PR 时，必须列出顺序、引用关系和兼容性检查，所有依赖在集成完成前不能对外宣称功能完成。**不得将跨模块接线/冲突留给后续机器人猜测处理。**
5. 跨领域调用遵循公共 `@alsvid/<domain>` facade、应用服务、outbox/事件或受控只读投影；不能跳过业务契约通过共享数据库的随意 SQL 直接篡改其他领域。权限、组织范围、订单及金额、库存台账、VIN 历史等已有不变量必须保留。

## 3. 不可随意新增的东西

未经负责人明确批准、记录 ADR、更新集成测试与迁移策略，**禁止**：
- 为单个模块/机器人开一个新的权威仓库、独立数据库、生产部署链路或第二套 API/鉴权/订单/库存/客户主档；
- 将已经共享的 Domain 复制成另一份业务实现，或者引入“临时兼容层”长期掩盖重复权威；
- 将业务领域拆为单独微服务，改变现有 `pnpm` 工作区、`apps/api` API 组合入口、领域边界和单一主账；
- 为方便开发向 AI、临时容器或 CI 分发生产 `DATABASE_URL`、R2 密钥，或在克隆/启动时自动对生产数据库执行迁移。

正常增加领域内文件、组件、独立前端页面、版本化 API、Docker 镜像/运行进程不等于拆系统，只要继续遵守单一业务权威、身份权限边界和集成契约。

## 4. 代码合并和联动验收（合并之前完成）

每个触及业务的 PR 必须写明：
- **涉及模块及链路**：源数据由谁写，其他模块如何读取/消费；是否涉及权限、订单、库存、财务、生产、VIN、售后等。
- **统一标识与契约**：新增/修改的 ID、状态、事件、接口、迁移、读写权威与向前兼容性；同一 PR 提交所有必要调用方变更。
- **跨模块验证证据**：相关单元/契约/集成测试实际运行结果。对影响核心链路的变更，验证 `SKU/BOM → 生产 → 库存/订单 → Vehicle/VIN → 车主/售后` 中受影响部分，不能只测试单页或孤立模块。
- **CI 门禁**：`node scripts/check-single-system-contract.mjs`、`pnpm arch:check`、相关测试、`verify` 与 `containers` 必须通过；本机没有跑、权限不足、CI 尚未结束，都明确记为“未验证”，不得谎称通过。
- **PR 交接**：基准 SHA、修改文件、关联 PR/Issue、已验证项、未验证项、依赖、数据库兼容/回滚方案。已有重叠 PR 时先沟通，必须在当前交付中解决冲突并回归，不允许覆盖另一机器人的成果。

只有**合并后的同一主干提交**通过受保护 CI、受控迁移及相应线上核验，才能分别宣称“代码已合并 / 部署已成功 / 业务联动已验收”。这些是不同状态。

## 5. 开发环境与唯一正式运行环境

- 多台机器和多个机器人是**开发/验证执行位置**，不是同时运行多个生产主系统。不同工作副本/分支不拥有第二套业务事实。
- 开发/CI 用独立临时数据库和存储；即使未来使用 Neon 云端开发分支，也必须与生产权限和数据隔离。正式生产由一个经过核验的发布链路及一套生产权威数据提供服务。
- 如需更换或新增生产运行平台，先确认唯一正式入口、Worker 单次执行/幂等、迁移发布权和回滚；不能因为镜像能在多台机器启动就默认所有实例都能修改正式数据。
- 现有 GitHub 任务分支 → PR → CI → 经授权的 Cloud Run 发布策略仍有效；修改该策略须有负责人批准与 ADR。不要把“同一程序可移植”误解为“每个开发机器人必须直连生产”。

## 6. 冲突处理优先级与执行责任

1. 本文件是已确认的**单一系统协作原则**；具体领域接口以代码、`docs/DATA_OWNERSHIP.md`、已生效 ADR、当前主干验证事实为准。出现冲突不得靠机器人个人偏好改架构，先在 PR 明确指出并提请负责人确认。
2. 在开始新独立系统、重建接口、迁移主账或改变部署权威之前**停止并报告冲突**，不得先做完再请求其他机器人合并。
3. 新 ADR 若要废止本契约，必须包含负责人明确授权、迁移/兼容性/联动验证计划及修订后的本文件，不能悄悄绕开。

## 7. 约束如何落地

- 通用 AI 入口：根目录 `AGENTS.md`；Claude 入口：`CLAUDE.md`；GitHub Copilot 入口：`.github/copilot-instructions.md`。三个入口必须指向本文件，并提示先读取当前主干。
- PR 模板必须要求填写跨模块联动影响与验证结果；`scripts/check-single-system-contract.mjs` 在 CI 的 `verify` 作结构性守门；原有 `pnpm arch:check` 和容器验收继续有效。
- **限制声明**：GitHub 文件无法强制未读取仓库的所有外部机器人自动接收，静态检查也无法证明所有业务流程正确。保障依靠入口规则 + PR 流程 + 分支保护/必需 CI + 真正的跨模块测试；不能把文字约束当成联动已实现的证明。

## 8. Admin 业务列表设计基线

- 订单、商品、库存等多条业务记录的管理列表默认采用紧凑表格；筛选条件和可用操作放在表格上方，空列表仍保留表头。
- 复用 Admin 共享的 `av-tablewrap`、`av-table`，分组记录标题复用 `av-table-record-meta`；不将每条记录设计成独立卡片，除非负责人明确要求。
- 保留原有业务数据、权限和操作；不以虚构数据或未接通的按钮填充界面。
