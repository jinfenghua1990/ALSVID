# ALSVID Admin — 业务模块信息架构（2026-10-23 调整）

> 状态：负责人确认「电商业务独立、经销商与 B2B 合并、生产制造、仓储物流、财务结算、客户车主、售后服务分域」的目标方向。
> 此文件明确**模块归属和页面入口**，不意味着所有 API、审批、营销、支付、仓库适配器或 B2B 下单已经交付。
> 保留原后台和已提交订单的唯一数据；不另建第二套商品、订单、库存和会计事实。

## 1. 顶部一级模块（业务分类，不等于微服务）

| 一级模块 | 统一 Admin 入口 | 左侧二级功能与边界 |
| --- | --- | --- |
| **工作台** | `/admin` | 跨模块待办 / 异常 / 经营概览；不得代替交易或财务事实 |
| **产品研发** | `/admin/product` | 产品类型（整车 / 配件 / 维修零件）、技术平台、型号、Variant、SKU、BOM、技术资料、版本和生产规格。唯一产品主数据 |
| **电商** | `/admin/ecommerce` | 官网商品审核与发布、首页商品绑定、**电商库存 SKU 台账查询**、DE/AT 商城售价、第一方 B2C 订单与草稿；未来可扩展品类展示、优惠券、购物车结账和 PSP 接入，但未上线前必须标记 |
| **经销商 / B2B** | `/admin/dealers` | 经销商档案、合作申请、授权、经销商试骑、B2B 产品目录 / 价格 / 订单协同（待按 Dealer/Commerce API 验收） |
| **生产制造** | `/admin/production` | 工厂计划、生产工单、装配、质检、生产需求、VIN 出生与工厂履约；不能把销售订单当生产工单 |
| **仓储物流** | `/admin/inventory` | 成品 / 零件库存、仓库与库位、盘点、调拨、第三方 WMS（预留）；出口物流、运输和清关已有 `/admin/logistics` |
| **供应链采购** | `/admin/supply` | 供应商主档、采购报价、采购订单、确认交期、来料和供应商质量；采购单不等于 B2B 销售订单 |
| **客户车主** | `/admin/customers` | 客户 / Partner、车主与账户验证、车辆归属、VIN、交付和购买/服务历史（仅显示真实已授权关联） |
| **售后服务** | `/admin/after-sales` | 保修申请、维修工单、配件申请、服务网点与车辆售后历史；配件商城**交易**仍属电商 |
| **财务结算** | `/admin/finance` | 应收、应付、单据、银行/PSP 交易证据、款项核对、退款/结算及汇率与到岸成本。支付执行属 PSP |
| **数据分析** | `/admin/analytics` | 汇总销售、渠道、生产、仓储、售后与财务数据，不修改事实 |
| **设置** | `/admin/settings` | 员工、角色权限、审计、系统集成、邮箱和架构知识 |

设计保持顶部一级导航 + 当前模块左侧二级导航；工作台全宽。桌面导航可以横向滚动，手机端横向/折叠菜单。禁止为了缩短导航把 B2C 与 B2B 订单合并进一个没有来源边界的页面。

## 2. 数据权威与跨模块链接

- **产品 ID**：同一个 Model 关联多个 Variant / SKU，产品中心维护唯一主记录；商城发布数据只引用 Model ID，售价只引用 SKU ID。一个商品详情页可以有多个 SKU（天猫式），不能在电商模块重新创建产品主记录。
- **订单**：B2C 官网订单由 Commerce 维护唯一订单记录；B2B 经销商交易由有授权的 Dealer/Commerce 协同记录，尚不具备的 B2B 操作必须显示待接入。旧 `/admin/orders` / `/commerce` 用于兼容书签、跨模块查询和现有订单 ID 深链，**不是第二套订单数据库**。
- **售后订单**：实物配件购买属于商城订单；维修申请、保修工单属于 Service。用 SKU / 订单 ID / Vehicle ID 跳转，不复制订单。
- **电商库存**：仅作为电商运营里的 SKU 库位读数，复用 Inventory 授权 API；展现现存、预留、台账可用和查询时间。不能把台账可用直接认作 DE/AT 商城可售库存，更不能双重统计 Vehicle/VIN 的实体车库存；跨仓履约资格、渠道配额、发布状态和商城售卖规则尚待实现。
- **仓储物流**：库存数量由 Inventory 流水负责，WMS 负责物理库位/拣包/收发货执行，Logistics 负责运输/清关/里程碑。订单中只能读取关联事实，不可直接伪造库存流水。
- **财务**：订单金额快照、已核验的 PSP 支付、应收应付义务是不同事实。收款、退款、核销由 Finance 和 PSP 协同，资金状态不可通过前端跳转或按钮伪造。
- **经销商身份**：Partner 是合法身份主档，经销商授权通过 Dealer 权限校验；Dealer Portal 与 Admin 不共用无界限的成员权限。
- **车主**：My ALSVID 属独立门户；Admin 内部客户记录不得仅凭邮箱相同自动认定 Vehicle 所有权。

所有权以 [DATA_OWNERSHIP.md](DATA_OWNERSHIP.md) 与 [ADR 0005](adr/0005-alsvid-owned-storefront-and-third-party-payments.md) 为准。

## 3. 这次代码迁移的范围（按门禁判定）

- 新 `/admin/ecommerce` 复用已存在的官网商品审核/发布、首页绑定与 StorefrontOrderDraftPanel，以及只读 Inventory 汇总查询。产品模块不再重复渲染这些电商发布表单，但保留产品 SKU 管理和跳转电商售价入口。
- 新 `/admin/finance` 复用已有 FinanceClient 的领域 API / 表单，新 `/admin/logistics` 复用已有 LogisticsClient。
- 旧 Admin 产品 / 订单 / 经销商 / 库存 / 供应链 / 售后路由保持有效。顶部导航按业务目的分类；Legacy AppShell 菜单也应保持名称一致。
- **尚未交付**：真实 B2B 订单门户完整闭环、统一跨渠道订单搜索、优惠券、正式公开付款、第三方 WMS 连接。新 UI 只显示已实现入口，其余标注待接入。
- 不修改生产数据库、订单归属或新建迁移；所有修改经 Draft PR 的 CI、浏览器预览、Review 后才能合并生产。不把设计示例数量当真实业务数据。

## 4. 实施与兼容注意

旧 `/product`、`/commerce`、`/inventory`、`/logistics`、`/finance` 等已有受保护页面继续可访问。统一 Admin 导航实现位于 `apps/web/app/_design/renderer.tsx`；原业务 AppShell 导航在 `apps/web/app/app-navigation.ts`。二者应由统一模块定义逐步收敛，不再新增第三套导航。

之前版本的“订单”独立一级导航改为 **电商（B2C）** 与 **经销商/B2B（B2B）** 的业务入口；订单数据模型不受本次菜单重组影响。若销售订单需要跨渠道全局查找，在工作台搜索或订单详情提供跨模块只读跳转，不让两个页面分别编辑同一订单。

其它约束沿用 [AGENTS.md](../AGENTS.md)、[Admin 真实工作区记录](ADMIN_LIVE_WORKFLOW_HANDOFF_2026-10-19.md)、[第三方仓接口规范](THIRD_PARTY_WAREHOUSE_INTEGRATION_2026-10-22.md)。不将本次 PR 视为全部业务闭环已经验收。
