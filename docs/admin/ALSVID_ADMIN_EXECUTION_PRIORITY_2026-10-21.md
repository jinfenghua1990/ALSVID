# ALSVID Admin：剩余修改的执行优先级（2026-10-21）

> 面向后续 AI 开发机器人。以 GitHub `main` 实际代码为依据；区分 **设计有稿 / 有领域 API / CI 通过 / 实际部署 / 业务验收** 五个状态，不得混为“完成”。

## 已核对的基线

- 正式主域名：`alsvidbike.com`；门户为 `www`、`admin`、`my`、`dealer`、`service` 等子域。不要新生成 `chaibenn.com` 或 `alsvid.com` 生产链接。
- 原先 PR #171 的 `ALSVID_ADMIN_MODULE_OPTIMIZATION_V1.md` 在 PR #174 被删除，本次已恢复为设计基准。
- 十大模块已在 `apps/web/app/_design/synced-screens.json` 中有对应菜单、字段、详情及演示流程；这些很多仍为 **fixture 演示数据**，不能宣称为真实订单、库存、销量、保修、交付记录。
- `apps/web/app/_design/integrated-operations.tsx` 已接入产品、订单、生产、库存、经销商、供应链的现有领域业务 UI，并接入客户查询、内部设置/审计、售后工单的部分功能；不要废弃或重复开发。
- 已成功的 WWW-only 发布：GitHub Actions [#39526913859](https://github.com/jinfenghua1990/ALSVID/actions/runs/39526913859)，Web release `0cc673b4`。它**不能证明**后端 API 新版、邮件、数据库迁移或每个 Admin 功能已在生产发布。
- 全栈部署仍有 Resend 发送域名 `alsvidbike.com` 未验证的外部配置阻断（见 `docs/RESEND_PRODUCTION_RECOVERY_2026-10-21.md`）；**不得绕过 Resend 验证、用旧域名或将发信密钥提权**。
- Shopify 负责 B2C/B2B 的商业订单和支付权威，ALSVID Admin 负责接收已证实的订单事实和内部履约；WMS 负责实际仓储执行。销售平台和内部运营台账不能互相冒充。

## P0 — 先确保可安全使用（阻断项）

| 事项 | 当前已知状态 | 下一步 AI 应执行 | 验收 |
|---|---|---|---|
| 规范与 GitHub 同步 | 十模块设计在代码中，原 #171 文档曾被 #174 删除 | 恢复设计规范；本优先级表作为总执行入口；保持 README/文档链接一致 | 新机器人能从 GitHub 找到十模块原规范和本清单 |
| 生产发布边界 | WWW-only 已成功，全栈邮件安全检查仍阻断 | 保留两条独立工作流；禁止前端发布执行 DB migration/API/Resend；全栈按安全门禁发布 | Web 发布记录显示正确 SHA，API/DB/Worker 未被修改 |
| 身份和权限 | Admin 有 `requirePortalSession('admin')` 守卫，后台 API 用自身权限判断；邮件 OTP 仍依赖 Resend | 检查跨门户权限、登录过期/401/403、登出与共享 Cookie；正式验证码实测待 DNS 验证 | 未登录、Customer、Dealer、Supplier 都不能访问 Admin 内部数据 |
| 禁止演示数据伪装 | Ardot 页面和很多详情是示例；现有真实业务组件可接入 | 全局审核“示例数值、按钮、提交、审批成功、同步状态”；无真实 API 的写入按钮必须禁用且解释原因 | 不会把假数据展示为生产库存、真实订单、客户保修、支付成功 |
| 代码质量 | CI 已包括 typecheck、tests、build、容器及数据库烟测 | 修复 CI / 运行期真实报错；回归测试及必要的日志追踪；不为“绿灯”跳过检查 | 每个 PR 的 verify + containers + 最终环境烟测通过 |

**P0 原则：** 邮箱外部 DNS 未完成不应冻结纯 Web 页面，但不能据此将全栈/API/登录验证码标成已可用；不要新增替代验证码后门。

## P1 — 一台车从型号到入库（最优先业务闭环）

1. **产品中心：** 平台 → 型号 → 版本/配置 → SKU → 生效 BOM → 工程资料。校验 BOM 发布版本、配置兼容、物料映射，不使用前端示例 `FC1 Pro / BOM V2.0` 作为真实事实。真实组件 `apps/web/app/product/product-client.tsx`，API `/v1/product`、`/v1/engineering`。
2. **生产中心：** 生产计划/工单关联已批准的型号、SKU、BOM 和物料来源；装配、QC、异常处理、复检、VIN 出生逐步写真实记录。真实组件 `apps/web/app/production/production-client.tsx`，API `/v1/production`、`/v1/vehicles`。
3. **库存中心：** 整车按 VIN、SKU、仓库/库位、可售/预留/质检/待交付分类；物料按 BOM/供应商关联；调拨、盘点、调整要有权限、审计、版本冲突保护。真实组件 `apps/web/app/inventory/inventory-client.tsx`，API `/v1/inventory`、`/v1/warehouse`。
4. **跨模块回链：** 型号详情 ↔ BOM ↔ 工单 ↔ VIN ↔ 库存按真实 ID 深链接；页面加载/无记录/无权限/网络失败明确呈现，不能点击 VIN 就凭此授予车主权限。

**P1 验收：** 在隔离测试数据库中用一条受控测试车型/工单完整演示“型号及 BOM 发布 → 生产/质检 → VIN 出生 → 仓库入库 → 各详情互相跳转”，每次写入可通过 ID、审计和数据库核对；不自动向正式仓库创造库存。

## P2 — 销售、交付、车主和售后链路

1. **订单中心：** 列表分开订单状态、付款证据、生产状态、物流状态、交付状态；真实商城支付必须由可信 PSP/Shopify 证据核验。管理页面展示已同步订单；退款审核不等于真正退款。见 `docs/ADMIN_ORDER_PAYMENT_REFUND_HANDOFF_2026-10-20.md`。
2. **交付与 VIN：** 订单行 ↔ 实际出库 VIN ↔ 物流 ↔ 经确认的交付事件；禁止只凭创建订单或物流“运输中”判定交付完成。
3. **客户/车主：** 客户档案和车辆所有权是不同实体；My ALSVID 车辆绑定需核验身份、真实交付与所有权证据。不得以邮箱相似、持有 VIN 或演示 Customer Partner 自动认定车主。
4. **售后：** 以真实 VIN/vehicle ID 建工单；引入受控保修资格核验、维修活动、配件申请到库存；区分“工单创建/已处理/最终维修完成”，保修初评不可冒充批准结果。

**P2 验收：** 真实来源订单与库存/交付/车辆归属/售后都有来源证据且不可越权；未接入的支付、ERP、物流和服务环节明确显示“未接通/待核验”。

## P3 — 经营辅助模块

1. **经销商：** 经销商档案、区域及店铺授权、B2B 订单、真实经销商库存、售后能力。Admin 是内部管理，Dealer Portal 是对外自助入口；不能混用权限与 UI。
2. **供应链：** 供应商、采购订单、供货零件及 BOM 关系、到货、质检、交期风险；Supplier Portal 后续提供上游供应商自助确认和履约，**不**让 Shopify 代替。
3. **数据中心：** 统一真实 KPI 口径（订单条目≠销量；余额行数≠库存台数）；标明期间、单位、同步时间、来源系统与权限，不可从演示图表推导真实销售额。
4. **设置中心：** 组织/工厂/仓库、员工角色、数据范围、审批策略、审计日志、集成状态和通知；敏感密钥只显示配置/连通性状态，不展示内容。

**P3 验收：** 各数字可下钻到其来源记录；角色和区域隔离可自动测试；没有集成的功能不出现“成功/已发送”。

## P4 — 体验与维护性（不抢 P1/P2）

- 保留现有顶部一级导航、左侧二级导航、浅色简洁卡片风格，不重做整体 UI。
- 逐页完善搜索/过滤/分页、空态/错误/重试、桌面及手机 1440px/390px，避免表格横向溢出。
- 重要操作先显示变更影响，再提交真实 API；无持久化服务时按钮禁用/只读，不制造“保存成功”假象。
- 原 Ardot 85 张图保留作设计参考，分批替换成统一真实组件；消费者端 WWW/My/Dealer Portal 使用独立 UI 规范。

## 推荐执行 PR 顺序

| 次序 | PR 范围 | 不得越界 | 关闭证据 |
|---|---|---|---|
| 0 | 规范恢复、本台账、README 链接 | 不改生产代码/服务 | PR、CI、主分支文档可读 |
| 1 | 产品型号/SKU/BOM 真实详情和校验 | 不新增第二套产品数据库 | 产品域测试、权限及浏览器 |
| 2 | 生产工单/QC/VIN 数据追溯 | 不创建假 VIN/生产完成 | 生产域集成测试和事务审计 |
| 3 | 库存台账/预留/调拨回链 | 不绕过 WMS 执行系统 | 库存账/出入库一致性测试 |
| 4 | 订单事实→交付→车主归属 | 不自行宣称已收款 | Shopify/PSP 来源与端到端核验 |
| 5 | 售后 VIN→维修→配件申请 | 不假承诺保修/库存扣减 | 服务域状态机、权限和证据 |
| 6 | 经销商/供应链/数据/设置 | 不复制 Dealer/Supplier Portal | 分模块验收与真实数据口径 |
| 7 | UI 全站细节、移动端、告警 | 不变更业务真相 | 浏览器截图和可用性验证 |

**所有 PR 必须标注**：需求对应、涉及代码、数据源、当前真实状态、是否涉及 migration、CI 结果、生产部署 run URL 和实际验收结果。修改代码、PR 合并、部署成功、业务可用四件事应分别记录。
